## §0 The defect, stated once (from source, not from the brief)

`internal/crypto/e2e.go:33-35` — `NewE2E(token)`: `key := sha256.Sum256([]byte(token))`. ONE key for every holder of the shared token. Concretely, three adversary classes can decrypt agent↔server traffic today:

1. Any relay holding the upstream token — relays present it at `relay_register` (`internal/relay/relay.go:306-317`, `Token: r.Token()`), so every relay on a chain holds it.
2. Any OTHER agent registered under the same token (`internal/server/server_token.go:119` `isValidToken` accepts primary + extra + rotated tokens fleet-wide).
3. Anyone who ever captured the token from agent config, command line, or token file.

The frame surface this protects is exactly two write/read paths: agent `writeMessage` → BinaryMessage (`internal/agent/agent.go:318-327`) and server decrypt in `handleMessages` (`internal/server/server_ws.go:289-293`). Both are per-connection, both consult one `e2eMgr`. The first envelope of a session (AgentInfo registration) is today plaintext by wire shape (`handleWebSocket` unmarshals `firstData` directly, server_ws.go:107-117) — this pre-existing plaintext-first frame is the negotiation slot this design uses; it is not a new surface.

**Milestone goal:** make the key derivable ONLY by the agent itself and its terminating server.

## §1 KEY DERIVATION — ONE mechanism, parameters fixed (Acceptance 1)

**Enrollment infrastructure that already exists at HEAD (measured):** the server runs a self-signed P-256 CA (`internal/server/enrollment.go:248` `loadOrGenerate`, persistence at `caDir/ca.crt|ca.key`) and issues per-agent certs with CN = agentID, 365-day validity (`:199` `SignAgentCert`, `:208` P-256 keygen, `:223` NotAfter, `:356-360` `curveForCA() = elliptic.P256()`). `POST /api/v1/enroll` (`:608` `handleV1Enroll`) exchanges a one-time enrollment token (`:83-88` ValidateToken: not-found / used / expired) for cert+key+CA PEM. This is the binding input the brief names. The design REUSES it; it does not add an issuance system.

**Derivation (single construction, no options):**

```
K_agent(session) = HKDF-SHA-256(
    IKM  = ECDH_P256_x(x_agent, X_CA)          // static-static ECDH, 32-byte X coordinate
    salt = SHA-256("probe/e2e-pa-v1" ‖ agent_id ‖ session_nonce_16B)
    info = "probe/e2e-peragent/v1"             // 21 bytes, ASCII
) → 32 bytes → AES-256-GCM key (same primitive family as e2e.go today)
```

- `x_agent` = agent's ECDSA P-256 private key from enrollment (never leaves the agent process).
- `X_CA` / `x_CA` = CA public/private key. Server side computes the SAME secret as `ECDH_P256_x(x_CA, X_agent)` — standard static-static ECDH property; both parties compute one identical shared point.
- `session_nonce_16B` = 16 random bytes per (re)connection, generated by the agent, transmitted in the OPEN inside the registration extension (§3). It is not secret; the strength lives in the IKM. It gives per-session key separation: a transcript captured in one session is useless for the next even without re-enrollment.
- The shared token is **not an input anywhere**. This is the load-bearing negative choice: including it would re-create the defect (every token holder = key holder).

**Why ECDH and not "HKDF over the cert public key" (the brief's example) — deviation D-1, with reason:** the public key, the CA cert, the agent id, and the nonce are ALL public material (certs are not secrets; the nonce rides plaintext by design; the CA cert is served to every client). HKDF over public inputs alone yields a key ANY party with the cert can derive — including a relay that witnesses the TLS handshake or reads the registration envelope. A derivation is only as secret as its most-secret input, so the input set MUST contain a private scalar. Static-static ECDH (agent cert key × CA key) is the minimal such secret already present at both endpoints, requiring no new key material, no new storage, and no new issuance. The cost is D-4 below (CA-key blast radius), named and accepted.

**Key strength (honest numbers):** ECDH P-256 = 128-bit security; the AES-256 key therefore CARRIES 128 bits despite its 256-bit length (stated so nobody over-reads the key size). Comparison: today's key carries exactly the entropy of the shared token — typically lower, never audited, and identical fleet-wide. Strictly stronger and the strength is now per-agent.

**Rotation story:**
- Per-session: automatic, via the nonce (every reconnect re-derives).
- Per-cert: re-enrollment (new keypair → new IKM). Cert lifetime is 365 days (enrollment.go:223); the existing enrollment-token flow (`POST /api/v1/enrollment-tokens`, api_v1.go:440-441) is the operator path. No new rotation machinery.
- Emergency per-agent: revoke (existing revocation set, server_ws.go:137 checked at connect) + re-enroll.

**Key schedule invariants:** one `K_agent` per (agent cert, server CA, session). GCM nonces remain random 12-byte per message (e2e.go wire format unchanged).

## §2 WHO KNOWS WHAT — the isolation criterion, with proof sketch (Acceptance 1)

**Allowed set (exactly two parties can derive K_agent):**
1. **The agent** — holds `x_agent`; computes ECDH with the public CA cert (`ServerCA` PEM, already delivered at enrollment, EnrollResponse field).
2. **The terminating server** — holds `x_CA` (CAManager, in memory) and receives the agent's cert in the registration extension; derives with the cert's public key.

**Excluded classes, each with its reason:**

| Adversary | Holds | Can derive K? | Why not |
|---|---|---|---|
| Downstream relay (incl. nested) | shared upstream token, all ciphertext on its wires | NO | Token is not an input (§1). Computing the ECDH output requires `x_agent` or `x_CA`; it holds neither. Witnessing the handshake or the plaintext registration extension gives only public values. |
| Any other agent (same shared token) | its own cert+key, shared token | NO | Its private scalar is bound to ITS cert; ECDH against `X_CA` yields its own key, not the target's. Deriving a sibling's key reduces to ECDLP on P-256. |
| Token thief (config/CLI/file capture) | shared token only | NO | As above — zero advantage; the shared token now authenticates the WebSocket upgrade and relay links but contributes NOTHING to any E2E key. |
| Malicious relay tampering with the extension | chain position | NO (integrity lost, never confidentiality) | Tampered cert/nonce → wrong K → GCM open fails on every frame → connection refused (§4 F-3). It can DoS a link; it cannot read one. |
| The terminating server itself | `x_CA` | YES — by design | It is the endpoint the traffic terminates at; "the server cannot read its own agents' traffic" is not achievable or desirable. The CA-key blast radius is named as D-4 (§6). |

**Proof obligation made precise:** K is computable iff one of {`x_agent`, `x_CA`} is known, given the public set {X_agent, X_CA, agent_id, nonce, transcript}. Restated: CA-key compromise = all agents' keys (server-side compromise class, already inside the allowed set); agent-key compromise = that agent only (containment the shared token never had).

## §3 NEGOTIATION FRAME (Acceptance 2/3)

**Pattern source (P17-01 §3, reused verbatim as doctrine):** a single OPTIONAL field, `omitempty`, honest absence for non-supporting parties — never `""`-stamped, never defaulted. That is exactly how `relayMetadata.Version` landed (relay_ws.go:16-23, mux.go:41-49).

**Extension — `AgentInfo` gains two optional fields** (internal/protocol/messages.go:246; the same struct already carries the ProtocolVersion compat pattern):

```go
E2ECert  string `json:"e2e_cert,omitempty"`   // agent cert PEM (public material)
E2ENonce string `json:"e2e_nonce,omitempty"`  // b64(16B session nonce), fresh per connect
```

`E2ECert+E2ENonce` both present = per-agent-key offer. Both absent = old/pre-cert agent (honest absence). One without the other = malformed, treated as absent (§4 F-1).

**Transport of the offer:** AgentInfo travels in exactly two frames today — the direct-socket first envelope (plaintext by wire shape, §0) and `channel_open`'s `ControlMessage.AgentInfo` (internal/relay/mux.go:26). Relays forward channel frames opaquely and never parse AgentInfo (verbatim doctrine: reviews/P21-03_PEERHELLO.md §3 zero-values section) — so the extension TRANSITS old and new relays unmodified with NO relay code change in this milestone (matrix row M-1). The brief's candidate (relay_register envelope extension) is declined as deviation D-2: the defect surface is agent↔server PAYLOAD traffic; relay_register negotiates relay LINK identity, a different traffic class. Per-agent keys bind to certs that only agents hold; relays holding no cert have nothing to negotiate.

**Key fingerprint for all logs/audit (redaction discipline, P17-01 §7 rule 5 applied):** `e2e_fp` = sha256(SPKI-DER)[:8] hex — the established `tokenFingerprint` shape (relay_identity.go:76-84). The cert PEM is public, but consistency beats cleverness: fingerprints in logs, never blobs.

**Server-side acceptance procedure at registration (direct socket and channel_open alike):**
1. Parse `E2ECert`; verify chain against THIS server's own CA (x509, CAManager pool) — never against any relay-supplied trust root (§4 F-3).
2. Identity bind: cert CN == connecting agent name; mismatch → refusal `E2E_CERT_IDENTITY_MISMATCH` (§4 F-3).
3. Revocation check (existing `RevokedAgents`, agent id) → refusal `E2E_CERT_REVOKED`.
4. Validity window with ±5-minute skew tolerance (§4 F-2).
5. Derive `K_agent`; session-fence it (§4 F-4). Decrypt failures from this agent thereafter are terminal for the session (GCM open failure ≠ retry shadow).

**Downgrade detection (both directions, no round-trip, no stall):** the agent try-opens inbound frames with `K_agent` first; a frame that opens ONLY under the shared-token key — or arrives as plaintext Text — IS the downgrade signal. Sticky for the session. The server's mirror image: an agent that registered no offer gets shared-token E2E with a loud event. Neither side ever probes with a question frame (old servers would never answer it; dead-wait per connect is a self-inflicted latency).

## §4 FAILURE MODES — each with the system's behaviour (Acceptance 2)

- **F-1 Revoked / stale cert.** Revoked (agent id in revocation set) or expired (`NotAfter` past, beyond skew) or unparseable or wrong CA: typed refusal `E2E_CERT_INVALID` (reason carries which AND both timestamps) via the established refusal frame (`writeForwardRefusal`, forward_policy.go:434; the P21-03 "exactly one answer" discipline). **No fallback to shared token** — fail closed. A broken key handshake is a security signal, not a compat case (same posture as P17-01 §5's unsealable-token = no-retry pre-state). Malformed offer (one field without the other): treated as no offer → loud shared-token downgrade (row M-1), never a half-derived key.
- **F-2 Clock skew on validity.** Validation window ±5 minutes in both directions around `NotBefore`/`NotAfter` (certs are already issued with a −1 minute NotBefore backstop, enrollment.go:~222). Outside the window → `E2E_CERT_INVALID` with the server's now and the cert's bounds in the reason. Skew can never strand an agent silently: the refusal reason is operator-debuggable on first reconnect.
- **F-3 Cert served by a malicious relay.** Three attack lines, each owned: (a) substitution — the server validates against ITS OWN CA pool only; a relay-supplied "CA" is never a trust root → chain failure → `E2E_CERT_INVALID`; (b) replay of another agent's valid cert — CN-to-name bind rejects it (`E2E_CERT_IDENTITY_MISMATCH`); and even a fully valid cert copy grants only public material (§2); (c) tamper/omit — omission is the loud-downgrade signal (§3), never a silent one (matrix rows M-1/M-4). Enrollment itself never transits a relay: `POST /api/v1/enroll` is an HTTP API on the server mux. Agent-side, MITM of the dial is already refused by P19-01's wss CA enforcement (the compat surface this unit absorbs).
- **F-4 Agent re-enrollment mid-session.** Key material is SESSION-FENCED: derived once at registration from the cert presented then, never re-looked-up per frame. Re-enrollment (new cert) therefore takes effect at the NEXT registration — no live-session key flap, no mid-stream decrypt breakage, no retroactive revocation of a running session. Named cost: revoking a cert does not cut a LIVE socket; the operator cuts sessions through the existing disconnect/rotate tooling. Honest, stated, accepted.

## §5 WIRE-COMPAT / ROLLOUT MATRIX (Acceptance 2 — all four combinations + transition)

Server posture ladder (single knob, three values, explicit wins): `e2e_enabled:false` (plaintext, honoured as today) < `e2e_enabled:true` default-ON with per-agent preferred, shared-token loud-downgrade tolerated < `--e2e-require-peragent` (strict: shared-token/plaintext agent traffic refused).

| Row | Client | Server | Behaviour | Loudness | Verdict |
|---|---|---|---|---|---|
| M-1 | old (no offer) | new, e2e on | shared-token E2E exactly as today | server: audit `e2e.downgrade` (AgentID, reason=`no_key_extension`, `e2e_fp` absent) + log; per-session `e2e_mode:"shared-token-legacy"` | allowed-loud (backward compat MANDATED — old fleet keeps working) |
| M-2 | old | new, e2e off | plaintext, unchanged | none needed (nothing encrypted; honest absence) | compatible |
| M-3 | new (offer, valid) | new | `K_agent`, full isolation; relays/siblings excluded per §2 | none (success is not an event) | target state |
| M-4 | new | OLD server (or new, e2e off) | agent's `e2e_key` fields ignored; inbound opens only under shared token or plaintext → agent downgrade detector fires (**default: REFUSE** — disconnect with downgrade notice, reconnect loop reports `E2E_SHARED_TOKEN_DOWNGRADE`, status surface carries the refusal code) | agent: log + status refusal; **operator opt-out `allow_shared_token_e2e:true`** flips refuse→continue-with-persistent-loud-log (P19-01 style: refuse + explicit flag, cf. `--allow-any-downstream`, relay.go:63 pattern) | loud-refuse by default; loud-continue only under an authored flag |
| M-5 | new WITHOUT cert (never enrolled — today's real population) | new | no offer ⇒ row M-1 treatment | as M-1 | allowed-loud; strict mode refuses with `E2E_KEY_REQUIRED` |
| M-6 | new behind OLD relay (chain) | new | extension transits opaquely (P21-03: relays never parse AgentInfo); isolation holds **even against that old relay** — the property P19-01 flagged as missing (per-peer downstream tokens) is delivered by key isolation, not by relay tokens | none | compatible — and the nested-relay `AllowAnyDownstream` exemption from P19-01's compat list is ABSORBED here: a nested relay may admit agents broadly, yet cannot READ them |
| M-7 | relay link traffic (relay_register, control frames) | any | unchanged, token-based, out of scope (D-2) | n/a | out of scope, named |

**Transition failure modes:** T-1 server restart mid-session → re-registration re-derives from the same cert (no change vs today). T-2 CA regenerated (`caDir` wiped, `loadOrGenerate` mints a fresh CA) → every presented cert fails chain → `E2E_CERT_INVALID` refusals fleet-wide, fail-closed, LOUD; remediation = re-enroll. T-3 ordering skew (agent upgraded before server anywhere) → row M-4; server first → row M-1; either order is loud on the side lacking support.

**Never-silent invariant (acceptance checked row by row):** every path where traffic could flow encrypted-under-shared-token or plaintext alongside a party that asked for per-agent isolation emits exactly one of: typed refusal, audit event, or persistent loud log. Zero paths are silent. The one candidate for silence — old server quietly decrypting new-client frames under the shared token — is closed on the AGENT侧 by M-4's refusal default.

## §6 ROLLOUT ORDER + ROLLBACKS (4 steps, each independently shippable)

| Step | Action | Observable | Rollback |
|---|---|---|---|
| R1 | Server accepts the extension (parse, verify, derive, session-fence, downgrade audit). Passive: changes nothing for a fleet with no certs presented. | audit `e2e.downgrade` events appear for M-1 population; `e2e_mode` on sessions | redeploy prior server binary (nothing persisted server-side — see D-3) |
| R2 | Enrollment issuance ramp: operators issue enrollment tokens; agents enroll (existing endpoints, existing flow — nothing to build). | certs issued per agent; `POST /api/v1/enroll` 201s visible in logs (enrollment.go log lines exist) | none needed (endpoint already at HEAD); unissued tokens expire on their own TTL |
| R3 | Agent upgrade: agents ship offer + downgrade-refusal default + `allow_shared_token_e2e` opt-out; delivered through the existing agent update channel. | `e2e_fp` in logs; row M-3 sessions observable | redeploy previous agent build (update channel is the rollback; keys derive per-session, so flight-back is clean) |
| R4 | Deprecate the shared token as an E2E input: strict flag `--e2e-require-peragent` (typed refusal `E2E_KEY_REQUIRED`); shared token REMAINS the auth/relay-link credential until its own rotation story (the token still authenticates the upgrade, server_token.go:119 — this milestone never touches auth). | refusals for M-1 population under strict mode; operators reconcile before enabling | drop the flag; server returns to R1 posture |

Order is mandatory: R1 must precede R3 (else every upgraded agent lands in M-4 refusals fleet-wide). R2 gates R3 only for agents that enroll; cert-less agents may run M-1 until enrolled.

## §7 DEVIATIONS from the P17-01 patterns — each named with its reason

- **D-1 Derivation input.** P17-01-style "hash/seal over named material" would suggest HKDF over the cert public key (the brief's example). REJECTED here: all-public inputs fail the isolation criterion (§1). Reason: a derivation is only as secret as its most secret input; ECDH with the CA key is the minimal already-present private input.
- **D-2 Negotiation surface.** Brief candidate: extend the `relay_register` envelope. USED INSTEAD: `AgentInfo` extension. Reason: agent↔server payload frames are the defected surface; AgentInfo is the registration frame agents own, it already follows the add-optional-field compat pattern, and it transits relays opaquely (M-1/M-6). Relay links keep token-based framing this milestone (out of scope, named).
- **D-3 No persistence change.** P17-01 added a serversDoc namespace; this design adds NONE. The server needs only the CA key (in memory) and the presented cert — every per-agent key is re-derived per session, so there is nothing to seal at rest and nothing to migrate. Reason: an unstoreable-key system has no at-rest surface by construction (stronger than seal-0600).
- **D-4 Accepted blast radius.** Terminating server holds `x_CA` ⇒ server compromise = all agents' keys (§2). Cost accepted because the server is the traffic endpoint regardless — key isolation's criterion is RELAYS + PEER AGENTS, and it holds exactly there. Mitigation named, not solved: CA key never leaves the CAManager process; rotation = CA regen + fleet re-enroll (F-T2, loud).
- **D-5 Refusal on downgrade is AGENT-side default-refuse, server-side allowed-loud.** Asymmetric on purpose: the old-client fleet (M-1) must keep working (server refuses nothing), while the new client actively defends ITSELF (M-4). One direction permissive, one conservative — neither silent.
